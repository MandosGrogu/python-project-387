# Тикет 006: Критерии приёмки спецификации

## Question

Что делает спецификацию «утверждённой» и готовой к раскладыванию тикетов? Каковы критерии полноты и однозначности?

## Type

## Resolution

**Критерии полноты (Completeness):**
- Описаны все три слоя (Data, Logic, UI): данные (схема БД или контракты API), логика (бизнес-правила, валидация, интеграции), интерфейс (ссылки на макеты для всех экранов и состояний).
- Проработаны негативные сценарии (Edge Cases): неверный ввод, падение стороннего сервиса, отсутствие интернета, пересечение прав доступа.
- Зафиксированы нефункциональные требования (NFR): производительность, нагрузка, безопасность, логирование.
- Определены критерии приёмки в формате GIVEN-WHEN-THEN.

**Критерии однозначности (Unambiguity):**
- Отсутствие двусмысленных слов — только конкретика (не «быстро», а «до 2 секунд»).
- Строгая терминология по глоссарию: сущности названы одинаково во всём документе.
- Единая интерпретация модальных глаголов по RFC 2119: MUST / SHOULD / MAY.
- Сложные алгоритмы и переходы статусов продублированы визуальными схемами (UML Sequence, Flowchart, State Machine).
