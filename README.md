# Календарь звонков


[![hexlet-check](https://github.com/MandosGrogu/python-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/MandosGrogu/python-project-387/actions)

Сервис бронирования встреч: клиент видит свободные слоты по 30 минут и оформляет запись, владелец календаря смотрит список предстоящих бронирований. Авторизации нет — все действия доступны любому посетителю.

Учебный проект Хекслета: https://ru.hexlet.io/programs/python

**Демо:** https://python-project-386-production.up.railway.app

## Стек

- Python 3.14+, Django 6.1+
- Tailwind CSS
- PostgreSQL (продакшн) / SQLite (разработка)
- uv — менеджер зависимостей
- gunicorn — WSGI-сервер

## Установка

```bash
git clone https://github.com/MandosGrogu/python-project-387.git
cd python-project-387
uv sync
```

Переменные окружения (необязательны, есть значения по умолчанию):

| Переменная           | По умолчанию                            | Назначение                              |
| -------------------- | --------------------------------------- | --------------------------------------- |
| `SECRET_KEY`         | небезопасный ключ для разработки        | ключ Django                             |
| `DEBUG`              | `True`                                  | режим отладки                           |
| `DATABASE_URL`       | `sqlite:///db.sqlite3`                  | подключение к базе данных               |
| `RECORDING_URL_BASE` | `https://recordings.example.com/`       | префикс ссылок на записи                |

Для продакшена задайте `DEBUG=False`, собственный `SECRET_KEY` и `DATABASE_URL`
в формате `postgres://user:password@host:5432/dbname`.

## Использование

```bash
# Применение миграций (при первом запуске)
uv run manage.py migrate

# Сборка стилей (необязательно — собранный tailwind.css уже в репозитории)
uv run manage.py tailwind build

# Сервер разработки
uv run manage.py runserver
```

Основные страницы:

- `/` — главная страница
- `/calendar/` — календарь месяца с бронированиями
- `/calendar/ГГГГ/ММ/ДД/` — свободные слоты выбранного дня
- `/calendar/booking/add/` — форма нового бронирования
- `/upcoming/` — предстоящие бронирования (страница владельца календаря)

## Docker

```bash
docker build -t call-calendar .
docker run -p 8000:8000 -e SECRET_KEY=<секретный-ключ> call-calendar
```

Приложение поднимется на http://localhost:8000. Для базы данных PostgreSQL
передайте `DATABASE_URL`, например:

```bash
docker run -p 8000:8000 \
  -e SECRET_KEY=<секретный-ключ> \
  -e DATABASE_URL=postgres://user:password@host:5432/dbname \
  call-calendar
```

Миграции в контейнере:

```bash
docker run --rm -e SECRET_KEY=<секретный-ключ> call-calendar python manage.py migrate
```

## 🤖 Автоматизация и AI-агенты (GitHub Actions + OpenCode)

В репозитории настроена экосистема автоматизации разработки, тестирования и аудита кода на базе AI-агента **OpenCode**  (события от ботов автоматически игнорируются).

### 🧠 Используемая модель
Во всех сценариях используется модель **`opencode/longcat-2.5-preview-free`**, развернутая в инфраструктуре провайдера.

### 📋 Список настроенных сценариев (Workflows)

| Название воркфлоу | Триггер запуска (Событие) | Что делает агент | Права токена |
| :--- | :--- | :--- | :--- |
| **`opencode`** | Комментарий в Issue/PR с командами `/oc` или `/opencode` | По команде `/oc fix` автоматически создает ветку `opencode/*`, правит код, проходит тесты, заливает коммит и **открывает Pull Request**. По команде `/oc explain` проводит текстовую консультацию. | `contents: write`<br>`pull-requests: write`<br>`issues: write` |
| **`opencode-review`** | Создание/обновление PR (`pull_request`) | Делает первый автоматический проход по коду. Проверяет стиль, типизацию и ищет очевидные ошибки, оставляя структурированные замечания в PR. Одобрение и мерж всегда остаются за человеком. | `contents: read`<br>`pull-requests: read`<br>`issues: read` |
| **`opencode-triage`** | Создание новой задачи (`issues: [opened]`) | Автоматически проводит триаж: анализирует суть проблемы, категоризирует её (Bug, Feature и др.), оценивает критичность и предлагает разработчикам краткий план действий. | `contents: write`<br>`issues: write` |
| **`opencode-cron-audit`** | По расписанию (`cron: '0 3 * * *'`) или вручную (`workflow_dispatch`) | **Ежедневно в 06:00 по Москве** запускает `Lighthouse CLI` в headless-режиме по адресу из `vars.LIGHTHOUSE_TARGET_URL`. Агент анализирует JSON-лог, прикрепляет HTML-отчет в артефакты, а найденные проблемы оформляет в виде **нового Issue**. | `contents: write`<br>`issues: write` |

### 🔍 Где смотреть прогоны и результаты?

1. **История запусков и логи**:
   - Перейдите на вкладку **Actions** в верхнем меню репозитория на GitHub.
   - В левой панели выберите интересующий вас сценарий (например, `opencode-cron-audit`).
   - Нажмите на конкретный прогон, чтобы увидеть пошаговые логи работы Lighthouse или инициализации Git-автора (`github-actions[bot]`).
2. **Скачивание отчетов производительности**:
   - Откройте любой завершенный прогон сценария `opencode-cron-audit`.
   - Прокрутите страницу в самый низ до раздела **Artifacts** (Артефакты).
   - Скачайте архив `lighthouse-performance-reports` с сырыми данными (`.json`, `.html`).
3. **Задачи и Пул-Реквесты**:
   - Результаты автотриажа и ночного аудита появляются в виде новых веток обсуждения в разделе **Issues**.
   - Исправления кода по команде `/oc fix` автоматически публикуются в разделе **Pull Requests** в виде связки с исходной задачей (`Closes #XYZ`).

### 📝 Опыт внедрения и самооценка интеграции

Внедрение AI-агента OpenCode позволило развернуть полную экосистему автоматизации (автокодинг, триаж, авторевью и регулярный аудит). В процессе интеграции были сделаны ключевые выводы:

* **Успешно с первого прохода:** Модель безупречно справляется с анализом багов, генерацией исправлений (включая тесты) и проведением первичного технического ревью. Изоляция контекста ботов и разграничение прав доступа (`read/write`) настроены стабильно.
* **Потребовало итераций (Особенности архитектуры):**
  * *Режимы работы:* Кастомный параметр `prompt` переводит экшен в режим текстовой консультации. Для нативного создания веток и Pull Request по команде `/oc fix` управление промптом должно быть полностью передано встроенному коду экшена.
  * *Авторизация Git:* Для бесшовного push изменений со стороны агента потребовалось принудительно настроить системный файл `~/.netrc` под учетные данные `github-actions[bot]`.
